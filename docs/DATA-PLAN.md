- **Schema**: migration 0004 adds nullable `mrp` (₹) to `wardrobe_items` and `buy_analyses`. Existing user rows keep `mrp = null` (never rewritten); new seeds carry the verified MRPs. Discount % is always computed at read time (`discountPctOf`), never stored.
- **Surfaces**: shared `PriceBlock` (selling price + struck-through MRP + "% OFF" badge) on Wardrobe cards, Smart Shop cards, Buy-or-Skip sample/result/history, and the Analytics cost-per-wear panel. Cost-per-wear stays price-paid ÷ wears in ₹ (server `costPerWear`), now labelled as such next to the MRP block.
- **User-entered prices**: Add Clothing scan form has Price paid (₹) + MRP (₹, optional, "on the tag") fields; Wardrobe Edit has the same pair; Buy-or-Skip custom analysis accepts an optional MRP and the verdict reasons cite the discount when ≥40% off. ## Shared data model & global state architecture (edit 2026-11-15 — user: "define a shared data model and global application state architecture… One wardrobe → powers the entire application")
- **Approach**: the server actions + database were already the single durable source every feature computed from; this edit adds the missing client-side layer the brief asks for — shared models, one global store, selectors, and a service layer — without redesigning the UI or replacing working components. No new state library (React Context + `useReducer`, per §14) and no schema migration (no new durable fields were needed).
- **Models** (`client/src/models/`): `user.ts` (UserProfile, UserPreferences), `clothing.ts` (ClothingItem with category taxonomy Tops/Bottoms/Shoes/Outerwear/Accessories/Ethnic Wear + subcategory list, ClothingAIAttributes), `outfit.ts` (Outfit — itemIds only, never embedded clothing objects; OutfitFeedback Love/Like/Neutral/Dislike), `styleDNA.ts` (StyleDNA, 8 affinities 0–100), `product.ts` (Product — source-agnostic: retailer today, official API/affiliate feed later), `purchase.ts` (PurchaseAnalysis BUY/CONSIDER/SKIP), `analytics.ts` (WardrobeAnalytics — derived, never stored), `insight.ts` (WardrobeGap + WardrobeInsight, one model feeding Smart Shop AND Analytics), `packing.ts` (PackingPlan — selectedItemIds only).
- **Mappers** (`client/src/services/mappers.ts`): the single translation point from the server wire contract to the models (e.g. server `price/wornCount/lastWornAt` → model `purchasePrice/timesWorn/lastWorn`; generated outfit factors → colorScore/occasionScore/weatherScore/styleScore). Fields the server doesn't have yet are explicit honest defaults documented in the model (fit "Regular", secondaryColors [], purchaseDate null, Product.rating null) — never presented in UI as measured data. ClothingAIAttributes values are deterministic derivations from the item's own fields (`selectors.deriveAiAttributes`), consistent with the app's standing rule that the scan is a "starting guess", not measured vision confidence.
- **Store** (`client/src/store/`): `WearWiseProvider.tsx` (owns the core React Query queries — items/saved/analyses/products/gaps/StyleDNA — exactly once under the same query keys the screens already used, hydrates the reducer with mapped models, exposes selector-derived analytics/insights/StyleDNA), `wearWiseReducer.ts` (WearWiseState: user, wardrobe, outfits, outfitFeedback, styleDNA, products, purchaseAnalyses, wardrobeGaps, insights, packingPlans, preferences, uiState; enforces §22 invariants — unknown IDs are no-ops, DELETE_CLOTHING leaves outfit itemIds dangling on purpose and `resolveOutfitItems` drops them at read), `actions.ts` (all §15/§16 action creators + SET_AI_STATE idle/loading/success/error per §23), `selectors.ts` (getTotalItems/getFavoriteItems/getUnusedItems/getMostWornItems/getCostPerWear/getColorDistribution/getCategoryCounts/getWardrobeHealth/computeAnalytics/computeStyleDNA/deriveInsights — health & dimension formulas mirror the server's getInsights so client-derived and server numbers agree).
- **Services** (`client/src/services/`): `storageService.ts` (the ONLY localStorage gateway — guarded safe-store moved here from App.tsx; persists session stub, theme, preferences, UI state; durable wardrobe data persists server-side in the artifact DB, which is the refresh-proof persistence layer of §20), `wardrobeService.ts` (list/add/update/delete/markWorn — MARK_OUTFIT_WORN bumps timesWorn+lastWorn for every piece in one call), `aiService.ts` (all §17 async operations incl. `analyzePurchaseFull`, which composes the stored verdict with detectDuplicates + wardrobe compatibility into the full §8 breakdown), `shoppingService.ts`, `weatherService.ts`.
- **UI integration (no redesign)**: App root wraps the shell in WearWiseProvider; Dashboard shows a one-line shared-state sync note whose numbers come from store selectors; Wardrobe wear/delete and Stylist/Dashboard outfit-worn + outfit-rating dispatch the central actions alongside the existing server mutations; Stylist generation drives SET_AI_STATE; Analytics gap cards read priority + matching-item counts from the same store WardrobeGap models Smart Shop uses. Landing marketing constants (CLOSET_PREVIEW, USE_CASES looks, BUY_SAMPLES) are editorial/demo content, not per-feature wardrobe state — the actual wardrobe was already single-sourced server-side and now also single-sourced in the client store.
- **Data-flow verification (§27)**: exercised against the sandbox via the published actions — login → addItem (new shirt) → listItems contains it (available to stylist/generator/analytics, which all read listItems) → generateOutfit returns outfits referencing real item ids → wearOutfit bumps the shirt's wornCount → analyzePurchase scores against the same wardrobe → deleteItem → listSavedOutfits still resolves gracefully (missing items filtered server-side, mirrored by resolveOutfitItems client-side) → rows persist in the DB across calls (refresh test).

## Login rate limiting (edit 2026-11-21 — user: "Add login rate limiting to WearWise (AUDIT issue 10)")
- **Scope**: the `login` action only. `demoLogin` (passwordless by design) and `register` are untouched; no UI redesign — the only client changes are the auth modal's error-phrase matching for the two new server messages, plus the platform v29 form upgrade below.
- **Schema**: migration 0009 creates `login_attempts` (email PK = lowercased email, failed_count, last_attempt_at, locked_until). A separate table, not fields on `profiles`, because unknown emails must be throttled too.
- **Rule**: 5 failed attempts within 15 minutes locks the email for 15 minutes. The lock is checked BEFORE PBKDF2 verification; a successful login deletes the attempts row (counter reset); failures on the first-login claim path (pre-auth account, password < 8 chars) count as failures. ## Long-term data behavior
- **Refresh policy**: No scheduled refresh — data changes only through user actions in the app. No cron.
- **Growth**: Wardrobe items, saved outfits, buy analyses, and wear events grow one row per user action; lists are capped server-side (limit params) and derived stats are computed from rows, never stored as frozen counters.
- **Ordering**: Wardrobe newest-first by default with user-selectable sort (most worn, least worn, recently added); saved outfits and analyses newest-first.
- **Time semantics**: `last_worn_at` and `created_at` are stored instants, rendered viewer-local; 'days since worn' is computed at read time from the stored instant. Cost-per-wear = price / max(worn_count,1), computed at read.
- **Real branded seed**: On first login (account creation) the login step inserts REAL_WARDROBE once (24 real branded products — e.g. GUESS black leather sneakers ₹4,500 ×42 wears, Mast & Harbour denim jacket ₹927 ×3 wears, Allen Solly olive shirt unworn 27 days, Manyavar kurta, Levi's 511 jeans) only when that user's wardrobe is empty. Rows are ordinary user rows afterwards: editable, deletable, never rewritten on read. Existing pre-upgrade accounts are migrated only by the user's explicit tap on the upgrade banner (`seedRealWardrobe`). Landing-page marketing sections (87-item closet visualization) are static product-preview content, visually distinct from the user's real dashboard numbers, which are always computed from their actual rows.
